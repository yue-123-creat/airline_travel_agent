# 小程序部署对齐说明 · 旅游回复图文混排

> **结论先说**：临时会话页（`app/static/chat.html`）已按「正文内 Markdown 出图」改过；**正式小程序端也必须改**，否则会继续出现「正文露出 `![名](url)` 字符串 + 图片全堆在气泡底部」的问题。  
> Agent 接口只负责把图文写进载荷；**谁渲染气泡，谁负责解析并原位出图**。

相关接口协议详见同目录 [`travel-reply-images-protocol.md`](./travel-reply-images-protocol.md)。本文偏**部署/联调 checklist**。

---

## 1. 为什么小程序也要改

| 层级 | 现状 | 小程序若不改会怎样 |
|------|------|-------------------|
| Agent | `answer` 里已可能含 `![景点名](URL)`；另有 `images[]` | 无影响（服务端已产出） |
| 会话预览页 | 已按 MD 原位拆成文字块 + `<img>` | 仅本地/Docker 预览可用 |
| 小程序气泡 | 若仍 `text` 整段展示 / rich-text 未开图片 / 只吃底部 `images` | **MD 原文露出来**，缩略图仍沉底 |

浏览器和小程序都**不会**自动把 `![]()` 变成图片，必须业务代码解析。

---

## 2. 必须对齐的行为（按优先级）

### 2.1 主路径：解析 `answer` 里的图片 Markdown（必做）

Agent 旅游支线会把高德/库内照片写成：

```text
![故宫博物院](http://store.is.autonavi.com/showpic/xxxx)
```

并尽量插在对应景点/时段文字后面。

小程序渲染助手气泡时：

1. **不要**把整段 `answer` 当作纯文本一次性 `setData` 显示（会露出 `![…](…)`）。
2. 用正则拆段，例如：`/!\[([^\]]*)\]\(([^)]+)\)/g`
3. 拆成块列表再渲染，例如：

```ts
type ReplyBlock =
  | { type: "text"; text: string }
  | { type: "image"; name: string; url: string };
```

4. WXML 侧：`text` 用文本组件；`image` 用 `<image mode="aspectFill" …>`，`referrer` / 防盗链按现网 CDN 策略（预览页用了 `no-referrer`）。
5. **同一条消息里**：若已从 `answer` 原位出图，**不要再**在气泡底部用同一批 URL 画第二遍画廊（避免「正文已有图 + 底部再堆一套」）。

参考实现：仓库内 `app/static/chat.html` 的 `hasMdImages` / `appendTextWithMdImages`。

### 2.2 兼容路径：结构化 `images`（建议保留）

当 `answer` **不含** `![]()` 时（旧消息、非旅游支线、降级回复），仍用响应里的 `images`：

| `placement` / `slot` | 展示 |
|----------------------|------|
| 无 `slot`，或 `placement: "footer"` | 气泡**底部** 1～3 张 |
| `placement: "inline"` 且带 `slot`（如 `第1天·上午`） | 按天/时段插在对应段落后 |

`slot` 格式：`第{N}天·上午|下午|晚上`。天标题可能带前缀，例如 `🗺️【北京三天两晚】第1天 …`，切段时以行内出现的 `第N天` / `DayN` 为准。

### 2.3 流式 `/v1/chat/stream`（若小程序走 SSE/分片）

| 事件 | 建议 |
|------|------|
| `token` | 可先追加文字；**流式过程中**正文可能尚无最终插图（插图多在收尾后写入） |
| `images` | 可预览；勿当成最终唯一来源 |
| `done` | **以 `done.answer` + `done.images` 做最终渲染**（覆盖预览） |

非流式 `POST /v1/chat`：直接用响应体的 `answer` + `images`。

### 2.4 历史消息回放

Agent 落库 assistant 消息 meta 里会带 `images`。回放时：

- 优先按当时存的 `content`（即 `answer`）做 **MD 解析原位出图**；
- 再按 `meta.images` 走兼容路径；
- 两套 URL 去重，避免双份。

## 3. 文案结构（展示侧可顺带对齐）

收尾模型已约束行程排版，小程序无需重写文案，但切段/样式可按此假设：

```text
🗺️【北京三天两晚】          ← 总标题只出现一次

第1天 故宫 → 景山 → 圆明园   ← 每天：景点A → 景点B → 景点C
上午：…
![…](…)
下午：…
晚上：…

第2天 八达岭长城 → …
…
```

- **不要**在 UI 上再给每天自动拼一遍总标题。
- 若要做「日卡片」样式，按 `第N天` / `DayN` 切天即可。

---

## 4. 域名与图片加载

- 图源多为高德：`store.is.autonavi.com` 等；小程序后台需配置 **downloadFile / 图片合法域名**。
- 部分图床对 Referer 敏感；若加载失败，对齐预览页策略（弱化 referrer 或走已备案 CDN）。
- 不要把图片 URL 再转成可点击的文本链接展示给用户。

---

## 5. 联调验收清单

- [ ] 普通推荐：无 MD 时底部 1～3 张；有 MD 时原位出图且不沉底重复  
- [ ] 多日行程：`answer` 内 `![]()` 出现在对应天/时段附近，小程序渲染为真实图片而非字符串  
- [ ] 总标题不重复三遍；每天可见 `景点→景点` 小标题  
- [ ] 流式：`done` 后最终气泡与非流式一致  
- [ ] 历史会话回放图文位置一致  
- [ ] 真机可加载高德图（合法域名 + 防盗链）

## 6. 和谁对齐

| 角色 | 对齐内容 |
|------|----------|
| Agent（本仓库） | `answer` 混排 MD；`images` 字段；SSE `done` |
| 小程序前端 | §2 渲染（**必做**） |
| 小程序 BFF（若有） | 透传 `answer`/`images`；或服务端预拆 `blocks[]` 再下发 |
| 运维 | 小程序合法域名、CDN/防盗链 |

预览对照：本仓库 Docker/本地打开会话页，同一句「安排北京三天两晚」——预览正确而小程序正文仍露 MD，即小程序渲染未对齐。
